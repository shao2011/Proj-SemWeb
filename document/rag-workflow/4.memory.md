# Memory — trạng thái thực tế

Tài liệu này mô tả **memory đang chạy thế nào**, không phải thiết kế dự định.
Thiết kế gốc ở [2.multi-turn-memory.md](2.multi-turn-memory.md) §3 và §6; những
chỗ code đi khác thiết kế được liệt kê ở §7 bên dưới, kèm lý do.

Code nằm gọn trong `backend/rag_ingestion/memory/`:

| File | Nội dung |
|---|---|
| `models.py` | contract, 3 scope, cap, closed key list, `MemoryStore` Protocol |
| `store.py` | implementation Postgres |
| `routing.py` | so sánh giá trị (`normalize`) và ngưỡng promotion |
| `tools.py` | 2 tool LLM gọi để lưu memory |

---

## 1. Ba scope

| Scope | Sống cùng | Cap | Chết khi |
|---|---|---|---|
| `thread` | một hội thoại | 10 | xóa thread (CASCADE) |
| `project` | một project | 30 | xóa project (CASCADE) |
| `user` | tài khoản | 50 | không bao giờ |

Cap chọn theo **tuổi thọ của scope**: thread và project là ngữ cảnh có điểm
kết nên giữ nhỏ; user scope sống lâu nhất nên rộng hơn — nhưng vẫn hữu hạn.
Prompt chỉ tải 25 item mỗi lượt, nên cap **quyết định cái gì bị quên**, không
phải cái gì được phép ghi.

Cascade đã kiểm chứng bằng test chạy trên Postgres thật: xóa thread thì memory
thread biến mất, xóa project thì memory project biến mất, user memory không
đụng tới.

## 2. Đường ghi: model tự quyết, trong lúc trả lời

Không có LLM pass riêng để trích memory. Model đang sinh câu trả lời **tự gọi
tool** khi thấy có gì đáng nhớ — pattern `bio` của ChatGPT. Hệ quả: 0 call LLM
thêm, và không cần bất kỳ danh sách từ khóa theo ngôn ngữ nào.

Tool nào có mặt là do **thread quyết định**, không phải model:

| Tool | Scope ghi vào | Có khi |
|---|---|---|
| `save_conversation_memory` | `thread` | chat thường |
| `save_project_memory` | `project` | thread thuộc project |
| `save_user_memory` | `user` | luôn luôn |

**Scope thuộc về tool, không thuộc về model.** Tên tool là hợp đồng; model
không có tham số nào để chọn sai scope.

### 2.1 Tham số có kiểu

Schema là pydantic model `SaveMemoryArgs`, nên JSON schema mang **enum thật**
chứ không phải một câu gợi ý:

```
key         MemorySlot   -- closed key list + "other"
custom_key  str | None   -- chỉ dùng khi key = "other"
value       str
type        MemoryType   -- fact | preference
```

Trước đây `key` là `string` kèm mô tả, và model thật đã trả về `name` và
`profession` — tiếng Anh đúng, key sai — mà store sẽ từ chối **sau khi câu trả
lời đã stream xong**, tức user không bao giờ được báo. Enum chặn tại gốc.
`normalize_key` vẫn còn nhưng chỉ phục vụ `custom_key`, nơi text tự do là điều
mong đợi.

### 2.2 Một lần ghi đi qua

1. **Giải slot** — key có tên thì dùng thẳng; `other` thì lấy `custom_key`
   chuẩn hóa thành `other:<slug>`. `other` mà không có `custom_key` → lỗi trả
   về cho model.
2. **Memory bật/tắt** — user tắt thì trả `skipped`, không đụng store.
3. **Trùng** — so với memory đã recall trong lượt này, **đã chuẩn hóa**
   (`normalize`: gộp khoảng trắng, bỏ phân biệt hoa thường). "Keep it short"
   nói lại thành "keep  it short " không tạo bản ghi mới.
4. **Ghi** qua `write_or_propose`.

### 2.3 Trong `_claim_slot` (atomic, dưới advisory lock)

- **Cùng key trong cùng scope → supersede**: bản cũ được đánh dấu xóa và trỏ
  `superseded_by`. Không bao giờ có hai giá trị mâu thuẫn cùng sống.
- **Scope đầy → evict**, không từ chối. Xóa dòng có `last_relevant_at` cũ
  nhất, kèm audit `DELETE`. Cap là ngân sách, không phải bức tường: một
  pipeline tự động mà không ghi được thì **âm thầm quên** thứ user vừa nói.
- **Chỉ evict dòng do pipeline ghi** (`llm_extracted`). Thứ user tự tay tạo
  (`user_explicit` / `user_confirmed`) là bất khả xâm phạm — scope đầy toàn
  loại này thì mới raise, và đó là lúc **proposal** có nghĩa.

### 2.4 Promotion local → global

Ghi thành công vào scope `thread` xong sẽ kiểm: key này đã xuất hiện ở **≥5
thread khác nhau** chưa? Có thì thêm một bản `user`.

- Chỉ `thread` đủ điều kiện. `project` là chuyện của project dù lặp bao nhiêu
  lần; `user` thì đã global sẵn.
- Promotion **thêm** dòng user chứ không di chuyển dòng thread — mỗi hội thoại
  giữ memory nó tự có.
- Ngưỡng 5 (thiết kế gốc ghi 2): một lần lặp là trùng hợp, còn promote nhầm để
  lại một global memory user không hề yêu cầu.

## 3. Đường đọc: mỗi lượt chat

1. **`recall`** — một query union cả 3 scope. Là union chứ không phải filter:
   dòng user scope có `thread_id = NULL`, lọc theo thread sẽ loại đúng phần
   global mà prompt cần.
2. **`_resolve`** — mỗi `key` chỉ giữ một memory, **scope hẹp thắng scope
   rộng**. Bản thua bị loại nhưng bản thắng được ghi chú "(this conversation
   only)" để model biết nó vừa đè lên một preference chung.
3. **`select_memories`** — cắt còn **25 item** (`MEMORY_MAX_ITEMS`), trần
   **2000 ký tự** làm lưới đỡ cho vài giá trị cực dài. Dòng được giữ nguyên
   vẹn hoặc bỏ hẳn, không cắt giữa chừng.
4. **Render** vào system message: mục `## About the user` (fact) và
   `## User preferences` (preference), phần bị bỏ được **nêu số lượng** chứ
   không im lặng.

### 3.1 Thứ tự

**Chọn thì xếp hạng, render thì theo alphabet.** Hai việc khác nhau có chủ ý:
system message mà đảo thứ tự dòng mỗi lượt là prompt prefix không provider nào
cache được, nên chỉ *dòng nào xuất hiện* thay đổi.

Xếp hạng theo 2 tín hiệu: **scope hẹp trước**, rồi `last_relevant_at` mới nhất.

Bản cũ xếp theo **alphabet của key** — và đó là bug thật: ba scope cộng lại
chứa nhiều memory hơn prompt tải được, nên key vần cuối không bao giờ vào
prompt, không bao giờ được đánh dấu đã dùng, và trở thành ứng viên bị evict
đầu tiên. Memory bị xóa **vì tên nó bắt đầu bằng "z"**.

### 3.2 `last_relevant_at`, và vì sao `last_used_at` đang NULL

```
last_relevant_at = last_used_at or created_at
```

Một mốc thời gian duy nhất, dùng chung cho **cả xếp hạng đưa vào prompt lẫn
chọn để evict** — hai bên không thể lệch nhau. Được tạo ra tính là lần đầu
tiên memory đó có ý nghĩa, nên thứ vừa lưu một giây trước không phải là thứ bị
xóa đầu tiên.

**`last_used_at` hiện không được ghi**, có chủ ý:

- Việc chọn là **tất định từ chính thứ hạng mà nó nuôi**. Lần xếp đầu tiên
  theo `created_at` chọn ra N cái; ghi `last_used_at` cho chúng khiến chúng
  đứng đầu lượt sau; nhóm còn lại không bao giờ ngoi lên. Nó **tự khóa kết quả
  ban đầu**, không thêm thông tin nào.
- "Được đưa vào prompt" **không phải** bằng chứng "được model dùng". Cột đó
  thực chất là *last shown*.

Cột và công thức được giữ nguyên, nên khi có tín hiệu thật thì bật lại chỉ là
một thay đổi nhỏ. Hàm `touch` đã xóa hẳn thay vì để lại không ai gọi.

**Hướng khảo sát (chưa làm):** phiên làm việc song song vừa dựng cơ chế model
tự khai `<!--used:s3,s7-->` cuối câu trả lời cho **summary item**. Đó chính là
tín hiệu memory đang thiếu — mở rộng marker sang memory id là con đường cụ thể
để `last_used_at` có nghĩa thật.

## 4. API cho user

| Route | Việc |
|---|---|
| `GET /memory` | liệt kê, lọc theo scope/thread/project |
| `POST /memory` | user tự thêm (`source = user_explicit`) |
| `PATCH /memory/{id}` | sửa giá trị, hoặc nâng lên user scope |
| `DELETE /memory/{id}` | xóa mềm |
| `GET /memory/proposals` | đề xuất chờ duyệt |
| `POST /memory/proposals/{id}/confirm` | duyệt thành memory thật |
| `DELETE /memory/proposals/{id}` | bỏ đề xuất |
| `PATCH /settings` | bật/tắt toàn bộ memory |

Frontend hiện chỉ hiển thị **user scope** (`Settings > Personalization`).
Memory scope thread/project và danh sách proposal **chưa có giao diện** — còn
treo.

## 5. Bất biến

- **Xóa là đánh dấu, không xóa dòng.** Mọi thao tác (ADD / UPDATE / DELETE) đều
  ghi audit, nên một lần ghi sai vẫn xem lại và hoàn tác được.
- **Một dòng sống trên mỗi (owner, scope, thread/project, key)** — enforce bằng
  partial unique index trong Postgres, không chỉ bằng code.
- **Cap và supersede là một quyết định**, chạy dưới `pg_advisory_xact_lock`
  theo scope: đọc dòng đang sống, quyết, ghi. Không có cửa sổ cho hai writer
  cùng chiếm slot cuối.
- **Mọi query đều lọc `owner_user_id`.** Đã kiểm bằng review đối kháng.
- **Closed key list.** Supersede khớp key chính xác, nên key tự do sẽ trôi
  (`occupation` lượt này, `job` lượt sau) và hai memory mâu thuẫn cùng sống.
  Ngoài danh sách phải đi qua `other:<slug>`.

## 6. Chi phí mỗi lượt

| Việc | Chi phí |
|---|---|
| Recall 3 scope | 1 query Postgres |
| Trích memory | **0** — đi kèm lượt sinh câu trả lời |
| Ghi memory | 1 transaction, chỉ khi model gọi tool |
| Đưa vào prompt | ≤25 dòng, ≤2000 ký tự |

Chat thường vì thế tốn **đúng 1 call LLM mỗi lượt**.

## 7. Khác thiết kế gốc

| Thiết kế (§) | Thực tế | Vì sao |
|---|---|---|
| Node `UnderstandMessage` trích memory (§3) | Model sinh câu trả lời tự gọi tool | Bỏ được 1 call LLM và toàn bộ heuristic theo ngôn ngữ. `UnderstandMessage` teo lại thành rewrite-only và chỉ chạy cho project chat |
| Scope suy ra từ key (§3.5) | Scope do tool quyết | Không còn gì để đoán. `route`/`scope_for` đã xóa |
| Promotion là *đề xuất*, ngưỡng 2 (§6.5) | Tự áp dụng, ngưỡng 5 | Không có ai ngồi duyệt đề xuất; ngưỡng cao bù lại |
| Cap đầy → đề xuất (§6.9) | Cap đầy → evict cũ nhất | Pipeline tự động không ghi được là âm thầm quên. Đề xuất chỉ còn cho scope đầy toàn memory user tự tạo |
| `memory` có type `pin` (§6.6) | Đã bỏ hẳn | Không có gì đọc nó. Ghim tài liệu, nếu làm, thuộc về file + filter retrieval, không phải một loại memory |
| Forgetting theo `last_used_at` (§6.8) | Chưa có; cột để NULL | Xem §3.2 |
| Budget memory theo ký tự | Theo số item | Ký tự làm việc bị cắt phụ thuộc memory hàng xóm dài hay ngắn |

## 8. Còn treo

Nghiên cứu nền cho các mục này ở [`4.lesson.md`](4.lesson.md) — đặc biệt §1
(cách đo "memory nào đã được dùng", có con số độ tin cậy) và §4 (vì sao
consolidation là hướng có bằng chứng nhất, còn LRU và decay thì không).

1. **LLM consolidation cho user scope** — gộp/dọn trùng lặp thay vì evict mù.
   Đã chốt hướng: đếm số lần evict, chạm ngưỡng thì chạy 1 call LLM ở khe sau
   `done`. Chưa build.
2. **Survey tín hiệu "memory thực sự hữu ích"** — xem §3.2.
3. **UI cho memory scope thread/project và cho proposal.**
4. **Promotion bị che**: bản `user` do promotion tạo ra luôn thua bản `thread`
   trong chính các thread sinh ra nó, nên không bao giờ được đánh dấu đã dùng ở
   đó. Chỉ "sống lại" ở thread mới. Đã kiểm chứng, chưa xử.
5. **Promotion không kiểm giá trị trả về** — user scope đầy toàn memory user
   tự tạo thì promotion âm thầm thành proposal.
