## [2026-08-24 22:50]
- **A dead login session now logs the user out instead of spamming 401s.** When a request comes back 401 with a stored token and no fresh one can be minted (the Firebase session is gone or its refresh fails), the client clears the token, resets to a fresh anonymous identity exactly like the sidebar's logout, signs the SDK out, and reloads in place. ## [2026-08-18 01:09]
- **Reranked hits far below the best one are no longer treated as evidence.** The chain took whatever `top_n` the reranker returned and put all of it in front of the model, so five barely-related chunks looked exactly like five good ones. There is now a cut at `keep_ratio` of the top hit's score, default 0.5, configurable via `RETRIEVAL_KEEP_RATIO`.
- **The cut is relative, not an absolute score floor, and that is the whole point.** Cohere's own guidance is that a relevance score is query-dependent, so 0.9 on one question does not mean what 0.9 means on the next, and this backend can be configured with three reranker families that share no distribution. An absolute floor would need recalibrating per query and per provider. A ratio needs neither. RAGFlow ships 0.2 and LlamaIndex ships nothing, which is roughly the state of the art on picking that number.
- **It can thin the evidence but never empty it.** `keep_ratio` is bounded at 1.0, so the best hit always clears its own floor. Two things that broke that guarantee and are now handled: a negative top score inverts the ratio and would cut everything including the argmax, so a non-positive top disables the cut; and the top is read with `max` rather than `ranked[0]` because nothing makes a reranker return its results in descending order.
- **Reference weighting deliberately still sees the cut leaves.** Found by a failing test, not by reading. Removing a cut leaf from the weighting does not remove its references, because Auto-Merge's promoted ancestor carries the union of its children's refs and `_selected_score` falls back to the strongest leaf underneath. So a cut leaf's references came back at the ancestor's strength and outranked references belonging to a leaf that survived. Cutting a chunk was promoting its references. `ranked` now keeps every scored leaf for the weighting and `evidence` is the filtered set that goes to Auto-Merge and to the model.
- Also: the cut runs before the ancestor lookup, so a dropped leaf costs no Qdrant round-trip, and `diagnostics["below_keep_ratio"]` plus a debug line naming each dropped chunk and its score make the loss traceable. `diagnostics["reranked"]` keeps its old meaning, the raw count the reranker returned.
- **Not built, on purpose.** No absolute floor, and so no "retrieval is weak" signal. Measuring one means labelling a few dozen queries, which samples the sample rather than the system, and the honest version needs an eval set that does not exist yet. Detecting a bad top hit is left to the model plus a search tool it can call again.
- Verified: 5 new tests (tail cut, best hit survives a 0.04 top score, ratio 0 keeps everything, signed scores disable the cut, config rejects a ratio above 1.0). Full suite 837 passed.

- **Thread summary gained the three mechanisms the ACE comparison said it was missing** (see `document/rag-workflow/3.lesson.md`), all behind the same rule as before: the model proposes, code owns structure and lifetime.
- **Duplicate guard (code).** An `ADD` whose text normalizes to a live item's is folded into a touch instead of minting a second copy. This closes a loop the prompt alone cannot: an `UPDATE` naming a hallucinated id is skipped by design, so the next fold sees the fact missing and re-adds it. Exact-match only — a semantic check would merge "deadline for A is 30/9" with "deadline for B is 30/9", and losing a real fact is worse than carrying a near-duplicate. Embedding-based dedup (what ACE does) deliberately not adopted.
- **The fold is two calls now: EXTRACT then CURATE.** Extract reads only the turns that scrolled out ("what is worth remembering"); curate reads only the distilled facts and the item list ("does this already exist, and where does it go"). One call doing both did each half worse; ACE measures the same split at +4.3 points. No facts extracted → the second call is skipped entirely. Either phase failing keeps the previous summary untouched, as before.
- **Items carry usage counters, and eviction ranks on them.** Stored inline as `[s3|u:4|f:9] text` — no migration, and lines written before counters read as zero. `u` counts answers that said they leaned on the item, `f` counts folds survived; eviction takes the lowest `u/(f+1)` among items with `f >= 1`, breaking ties toward the item that has had the most chances. This fixes the failure plain LRU has: a fact that is right the first time is never UPDATEd, drifts to the front, and dies before a newer item nobody has ever used. Items minted by the current fold are never the victim — their zero score means "no chance yet", not "failed".
- **`u` comes from the model, not from string matching.** The answering prompt (only when the summary section is present, so short chats pay nothing) asks for a trailing `<!--used:s3,s7-->`. New `summary/marker.py` filters it out of the live stream: nothing after a `<!--` is emitted until the closing `-->` decides what it was, and an unterminated comment is dropped whole — which is also why a turn stopped mid-marker leaves nothing dangling, the bytes were never sent. Ordinary HTML comments in the answer pass through untouched. A missing marker is logged and credits nothing; ids the summary does not hold are ignored.

## [2026-08-08 20:55]
- **Added a whole-outcome retrieval cache in Redis** (`retrieval/cache.py`). A query costs one embedding call, three or four Qdrant searches, and one rerank over the entire candidate pool; the reranker charges per document it scores, so caching the finished `RetrievalOutcome` is the only thing that skips that cost rather than shaving it.
- **Off by default** (`RETRIEVAL_CACHE_ENABLED=false`). Whether it earns its keep depends on how often the same question recurs in the same project, which is a property of the deployment and not of the code. Turning it on is a deliberate choice; hit and miss are logged at INFO so the rate can be measured rather than argued about.
- **The key carries every input that changes the result**: owner, project, query, rewritten query, embedding profile, the whole `RetrievalConfig`, limit, and language. A parametrised test asserts that changing any one of them misses — a key that ignored one would serve an answer computed for a different question.
- **A completed upload invalidates the project.** Each project has a Redis version counter that a successful upload bumps, and the counter is part of the key, so every entry for that project becomes unreachable at once. Without it, a user who asks the same question after uploading would never see the document they just added and would get a confident citation to the older evidence instead. Invalidation runs *before* the `done` event, so a client that queries the moment it sees `done` already reads through the new version. A failed upload does **not** bump: nothing was indexed, so nothing cached became wrong, and bumping would discard every valid entry over a bad file.
- Invalidation bumps a counter rather than scanning and deleting keys: `SCAN` over a large keyspace on the request that just finished an upload is slow, and the orphaned entries age out under their own TTL and the existing `allkeys-lru` policy.
- Best-effort throughout: every Redis failure and every unreadable entry degrades to a miss, because a slow retrieval still answers and a raising one does not. TTL defaults to 15 minutes — far shorter than the 24h embedding cache, because an embedding is a pure function of (text, model) and never goes stale while an outcome is only valid for the documents that existed when it ran.

Fixed the fake, then **verified against real Redis** that `INCR` and `GET` share a keyspace and that `GET` returns `b'1'` — which is why the implementation decodes bytes.
